- ~~SODAX introduced partner API keys; bring our infrastructure in line (David, 2026-09-15)~~ → **Done.** Read of the surface first: the app's entire browser-side SODAX HTTP traffic is three POSTs, all hung off the SDK's one `solver.solverApiEndpoint` knob — `/quote` (useQuote), `/status` (useStatus) and `/execute`, the notify inside `vaultSwap` that tells the solver a pour has landed and to go fill it. Everything else is on-chain or the ICON relayer, which is not SODAX API. `/execute` is a write, SODAX's write routes are already wired for the key check, and enforcement comes back on route by route — so today's pours keep working and a future flip would kill them silently. The key itself can never ship to the browser (a key in front-end JavaScript is a published key, as their docs put it plainly), so: `solverApiEndpoint` now resolves to `${window.location.origin}/api/sodax/intent` in the browser and stays upstream on the server, and `app/api/sodax/[...path]` attaches `x-api-key` from `SODAX_API_KEY` and forwards. The proxy is deliberately transparent — upstream's status, body and content type pass through untouched, because the SDK reads `response.ok` then `response.json()` on both branches and the app's error copy reads the solver's own envelope — and deliberately narrow: `lib/server/sodax-proxy` allowlists exactly those three routes, since a pass-through would lend our credential to every path on the SODAX API.
